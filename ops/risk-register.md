# Risk Register

Top 10 risks, ordered by the product's own exposure rather than by generic
industry rankings. Likelihood and impact are the founder's current judgment,
not a computed score; they should be revisited at each quarterly review
(`access-control.md`). Owner is the accountable person today — for every row
that is effectively the founder, that is stated plainly. Status uses the same
BUILT / PARTIAL / PLANNED vocabulary as the control matrix.

| # | Risk | Likelihood | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|
| R-01 | **Single-founder bus factor.** One person holds deploy access, database access, vendor relationships, the incident response role, and all institutional knowledge. Illness, burnout, or simple unavailability halts operations and incident response — including during a breach, where regulatory clocks keep running. | High (certain by definition) | High | Document runbooks in this package (deploy path, break-glass in `access-control.md`, IR steps in `incident-response.md`); establish one named emergency backup person with scoped access and a walkthrough; keep env contract current (`deploy/env-contract.md`). | Founder (CEO) | PARTIAL — documentation largely exists; backup person not yet designated |
| R-02 | **iMessage/Photon platform dependency.** The product's primary delivery surface is iMessage via phone numbers registered through Photon (`registerPhotonUser` in `deploy/hire-api.ts`, `PHOTON_PROJECT_ID`). Photon policy changes, number reclamation, or Apple-side friction would sever the core interaction channel with no fallback. | Medium | High | Monitor Photon account health; keep the web brief surface working as a degraded-mode channel; document number inventory; ⚠ COUNSEL to review Photon terms for number ownership and termination rights. | Founder (CEO) | PARTIAL — dependency understood; no secondary messaging channel |
| R-03 | **Credential theft via browser task.** The browser worker handles real user credentials and one-time payment cards in memory (`consumeVaultCredential`, `retrieveCapabilityBoundLinkCard` in `deploy/browserWorker.ts`). A compromised task, a malicious page, or a worker compromise could expose credentials. Mitigations in code: capability-digest-bound consumption, E2B fresh-sandbox-per-task, origin-bound vault consumption, SSRF blocklist. | Medium | High | Keep E2B isolation enabled in production (`resolveBrowserExecutorMode`); never re-enable local Chromium without explicit flag; capability digests fence every credential scope; audit events record consumption; pen test scope includes this surface (`pen-test.md`). | CTO (acting) | BUILT (controls) — pen test not yet run |
| R-04 | **Stripe account compromise.** Full control of billing, customer PII, and payout configuration. Phishing of the founder is the realistic path given the single-person team. | Low-Medium | High | MFA on Stripe; restricted API key only (per `deploy/env-contract.md`, never the root key); webhook secret rotation procedure documented; monitor Stripe dashboard alerts; enable Stripe's own fraud/notifications. | Founder (CEO) | PARTIAL — key scoping documented; per-account MFA verification not yet recorded |
| R-05 | **Database misconfiguration or exposure.** Postgres runs on the same VPS (`vmi2997871`) as everything else; a misconfigured firewall, a leaked `DATABASE_URL`, or an over-broad role exposes all customer data at once. | Medium | High | `DATABASE_URL` only in Coolify env (never repo); `/readyz` proves DB reachability but does not expose data; row-level user scoping in every query (`WHERE user_id = ...` throughout the codebase); ⚠ AUDITOR will ask for evidence the database is not internet-exposed — verify Hetzner firewall rules and record the answer. | CTO (acting) | PARTIAL — code-level scoping BUILT; network exposure verification not yet recorded |
| R-06 | **Prompt injection during web tasks.** A web page the agent visits can contain instructions targeting the agent (in page text, or via search results parsed in `deploy/webSearch.ts`). Injection could attempt exfiltration, unauthorized navigation, or purchase manipulation. | High (attempted eventually; exploitability is the question) | Medium-High | Architectural fences, not prompt-level hope: payments require user-approved capability grants bound to merchant origin and exact amount (`capability_grants` + digest); purchases count as success only with an explicit merchant order confirmation (`hasMerchantOrderConfirmation`); credentials consumed only against the approved origin; SSRF blocklist (`deploy/browserNetworkPolicy.ts`); no code-execution path from page content; sandboxed E2B environments. | CTO (acting) | BUILT (core fences) — ongoing red-teaming of the agent loop is PLANNED |
| R-07 | **Compliance gaps becoming customer-facing claims.** The privacy page promises full deletion within 30 days, but the in-product purge covers trust tables only (README discrepancy 2), product log tables are plaintext (EN-3), DPAs are largely unsigned (`vendors.md`), and no DPIA exists. A gap that is documented and planned is a finding; the same gap in front of a regulator or journalist is a crisis. | Medium | High | This package is the gap list; close DS-1 (full account deletion), EN-3, VD-1 DPAs, and PG-3 DPIA before scaling marketing claims; ⚠ COUNSEL review of privacy page promises versus actual flows. | Founder (CEO) (Privacy vacant) | PARTIAL — gaps documented; closure dates not set |
| R-08 | **Loss of audit/monitoring visibility.** Detection currently depends on the founder noticing: Coolify alerts, `/readyz` failures (`deploy/web-server.ts` returns 503 on DB failure), bot delivery anomalies. There is no central log aggregation, no alerting on the trust tables, and `verifyAuditChain` is never invoked in production (control-matrix AL-4). | Medium | Medium | Ship AL-4 (scheduled chain verification); enable Coolify's built-in notifications; add bot delivery anomaly checks to the existing loop infrastructure (`setInterval` patterns in `deploy/web-server.ts`); reconsider a hosted log sink. | CTO (acting) | PLANNED |
| R-09 | **Single-server availability.** All workloads (web, bots, browser worker, Postgres, OpenBao, Plausible) run on one Hetzner VPS. Hardware failure or provider incident is a total outage, and if no backup exists (README discrepancy 5), potentially total data loss. | Low-Medium (per-year) | High | Establish and test backups (BK-1 — prerequisite for everything else); document a restore procedure with a measured restore time; evaluate a second region or at minimum off-VPS backups; OpenBao transit keys make DB restores re-encryptable per-user only if OpenBao itself is backed up — include it. | Founder (CEO) | PLANNED |
| R-10 | **Contractor over-access.** Contractors receive scoped repo access today, but as the team grows, access tends to accumulate faster than it is removed. A departing contractor retaining deploy or DB access is a silent, high-impact exposure. | Low-Medium | Medium | Access-control policy in `access-control.md` (joiner/mover/leaver); quarterly access review (AC-4) before any second person gets production access; contractor access via scoped GitHub permissions rather than shared credentials; no shared accounts, no exceptions. | Founder (CEO) | PARTIAL — policy written; review cadence not yet operating |

## Explicitly out of the top 10 (but watched)

- **AI model provider lock-in (GMI/DeepSeek).** Swap-ability is a business
  risk, not a security or privacy risk at current scale; model calls are
  centrally configured (`GMI_API_KEY`/`GMI_BASE_URL`/`GMI_MODEL` per
  `deploy/hire-api.ts`) and the vendor inventory tracks the data flow.
- **Payment double-execution.** The capability state machine, digest fencing,
  and the no-replay-on-uncertain-outcome rule in `deploy/browserWorker.ts`
  (failed tasks are never retried) make accidental double charges the kind of
  bug the pen test should try to prove impossible, rather than a standing
  operational risk.
